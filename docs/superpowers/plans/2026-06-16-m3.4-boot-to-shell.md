# M3.4 — Boot to Shell (initramfs load + DTB initrd nodes → interactive busybox shell) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

> **Assumption (M3.3 not yet written):** the concurrently-authored `2026-06-16-m3.3-virtio-console.md` plan is **absent** at the time this plan was written. This plan therefore designs against the following **M3.3 contract**: by the end of M3.3 the guest exposes an interactive virtio-console as `hvc0` (virtio-mmio transport at guest IPA `0x0A000000`, used-buffer IRQ injected via the M3.2 vGIC), and the earlier PL011 passthrough (`ttyAMA0`, IPA `0x09000000`) from M3.0 remains available. Where this plan chooses a console it states the choice and the fallback explicitly so it holds whether or not M3.3 landed virtio-console.

**Goal:** Supply a small busybox `cpio.gz` initramfs to the already-booting Linux guest, place it in guest RAM via QEMU `-device loader`, and advertise it to the kernel through the guest DTB `/chosen` `linux,initrd-start` / `linux,initrd-end` properties — so the kernel unpacks it as the root filesystem, runs `/init`, and drops to an **interactive busybox shell prompt** (`/ #`) on the console. This is the headline M3 definition of done.

**Architecture:** This slice is **pure build/dts/run integration — no hypervisor `.c` change**. The kernel discovers the initrd location entirely from the DTB `/chosen` `linux,initrd-start`/`linux,initrd-end` properties (guest IPA values), and QEMU's `-device loader` places the raw initramfs bytes at a fixed **physical** address inside the guest-RAM backing window. The hypervisor's Stage-2 already maps the whole guest-RAM 1 GB block (IPA `0x40000000`–`0x7FFFFFFF` → PA `ram_pa`), so the initrd bytes are reachable by the guest with no new mapping and no hv code. The initramfs is **user-supplied** (like the kernel `Image`), driven by an optional `LINUX_INITRD` env var so M3.0–M3.3 runs without an initramfs keep working unchanged.

**Tech Stack:** GNU Make, `dtc` (Device Tree Compiler), QEMU `qemu-system-aarch64` ≥ 6.0 with `-machine virt,gic-version=3`, an externally-built static busybox + `cpio`/`gzip` to produce the initramfs (host tools, not in-repo). No hypervisor C/asm change in this slice — C11 freestanding build is untouched.

## Address Map (extends the M3.0/M3.3 map — pinned)

These build on the M3.0 map (`2026-06-16-m3.0-linux-alive.md`). M3.4 adds **one** entry: the initrd.

| Name | Guest IPA | Physical (PA) | Size | Notes |
|---|---|---|---|---|
| Guest RAM base | `0x40000000` | `0x48000000` | 256 MB | Backing window `0x48000000`–`0x57FFFFFF` (M3.0). |
| Kernel `Image` | `0x40080000` | `0x48080000` | — | `text_offset` `0x80000` (M3.0). |
| Guest DTB | `0x42000000` | `0x4A000000` | ≤ 32 MB headroom | 32 MB above RAM base (M3.0). |
| **Initramfs (NEW)** | **`0x44000000`** | **`0x4C000000`** | **≤ ~16 MB reserved** | 64 MB above RAM base. See arithmetic below. |
| virtio-mmio (M3.3) | `0x0A000000` | — (MMIO hole) | 4 KB | Trap-emulated; not RAM. |
| PL011 passthrough | `0x09000000` | `0x09000000` | 4 KB | Identity Device-nGnRE (M3.0). |

### Initrd address arithmetic (show-your-work, required by spec)

- **Chosen PA:** `0x4C000000`.
  - Inside the backing window? Window is `0x48000000`–`0x57FFFFFF`. `0x4C000000` = `0x48000000` + `0x04000000` = **64 MB into the 256 MB window**. `0x4C000000` < `0x57FFFFFF`. **Yes, inside.** ✔
- **Corresponding guest IPA:** PA→IPA for RAM subtracts the M3.0 RAM offset `0x08000000`: `0x4C000000` − `0x08000000` = **`0x44000000`**. Equivalently IPA = RAM_IPA + 64 MB = `0x40000000` + `0x04000000` = `0x44000000`. ✔
- **Above the kernel?** Kernel loads at IPA `0x40080000` and a defconfig arm64 kernel's static image + early `.bss` + early page tables + decompression scratch is comfortably under a few MB to ~32 MB above the load. The DTB already sits at IPA `0x42000000` (32 MB). The initrd at IPA `0x44000000` is **64 MB above RAM base, i.e. ~63.5 MB above the kernel load and 32 MB above the DTB** — comfortably clear of the kernel's early runtime footprint. ✔
- **Headroom for the initramfs payload:** from `0x44000000` to the next pinned consumer there is nothing else placed in RAM until the top of the 256 MB window (`0x4FFFFFFF` IPA / `0x57FFFFFF` PA). A busybox `cpio.gz` is typically 0.5–4 MB; we reserve a generous **16 MB** window (`0x44000000`–`0x44FFFFFF` IPA) for it, leaving ~191 MB of RAM above for the kernel page cache / unpacked rootfs (an initramfs unpacks into a tmpfs that grows in normal RAM, not at the load address). 16 MB reserved is plenty and not wasteful since it is only an address reservation, not a memory carve-out. ✔
- **Verdict:** 64 MB offset is the right choice — not too tight (well above kernel + DTB), not too generous (leaves the bulk of RAM free). Keep `0x4C000000` / IPA `0x44000000`.

QEMU `-device loader,addr=` always takes **physical** addresses (so `addr=0x4C000000`). The `.dts` `linux,initrd-*` properties use **guest IPA** values (so `0x44000000` and `0x44000000 + size`).

## Does the hypervisor need a `.c` change? (verified — NO)

Reasoning, confirmed by inspection of the M3.0 plan and the boot contract:

1. The arm64/Linux initrd discovery path is **DTB-only**: the kernel reads `/chosen/linux,initrd-start` and `/chosen/linux,initrd-end` (guest IPA) and maps that range from its own RAM. The hypervisor passes the DTB IPA in `x0` (M3.0 boot protocol) and is not otherwise involved.
2. The bytes are placed by QEMU `-device loader` at a **physical** address inside the guest-RAM backing window. The hv Stage-2 already maps the **entire** guest-RAM 1 GB block (`l1_table[1]`, IPA `0x40000000`–`0x7FFFFFFF` → PA `ram_pa`, Normal WB) per M3.0 Task 4 — so IPA `0x44000000` (PA `0x4C000000`) is already reachable. No new Stage-2 mapping.
3. Nothing in the hv touches "initrd": M3.0's `vm.c`/`vm_config.h` carry only `entry`, `mem_base`, `ram_pa`, `mem_size`, `dtb_ipa`. There is no initrd field and none is needed — the kernel never asks the hv for it.

**Conclusion:** M3.4 modifies only `scripts/run-qemu.sh`, `guest/qemu_virt.dts`, `CLAUDE.md`, and adds one docs file. **Zero hypervisor C/asm changes.** `readelf` entry stays `0x40080000` trivially (no link inputs change).

### Task 1: Add the optional initramfs loader to `scripts/run-qemu.sh`

**Files:**

The M3.0 script loads `Image` (`addr=0x48080000`) and `guest.dtb` (`addr=0x4A000000`). M3.4 adds a **third, optional** loader for the initramfs at PA `0x4C000000`, only when `LINUX_INITRD` is set — so existing M3.0–M3.3 runs (no initramfs) are byte-for-byte unaffected.

- [ ] **Step 1: Rewrite `scripts/run-qemu.sh` to add the optional initrd loader**

Replace the whole file with (this is the M3.0 script plus the gated initrd loader; it preserves the M3.0 `LINUX_IMAGE` / `GUEST_DTB` behaviour exactly):

```sh
#!/bin/sh
set -eu

# Boot an unmodified arm64 Linux Image as the guest.
#   LINUX_IMAGE  — path to a prebuilt arm64 'Image' (required)
#   GUEST_DTB    — path to the compiled guest DTB (default: build/guest/guest.dtb)
#   LINUX_INITRD — (M3.4, OPTIONAL) path to a busybox cpio.gz initramfs.
#                  If unset, no initramfs is loaded (M3.0-M3.3 behaviour).
#
# Physical load addresses MUST match the hv address map (board.h) and the
# guest .dts (guest IPA = PA - 0x08000000 for the RAM region):
#   Image   @ PA 0x48080000  (guest IPA 0x40080000)
#   DTB     @ PA 0x4A000000  (guest IPA 0x42000000)
#   initrd  @ PA 0x4C000000  (guest IPA 0x44000000)  <- must match dts linux,initrd-start
: "${LINUX_IMAGE:?LINUX_IMAGE must point to a prebuilt arm64 Image, e.g.: LINUX_IMAGE=/path/to/Image make run}"
GUEST_DTB="${GUEST_DTB:-build/guest/guest.dtb}"

[ -f "$GUEST_DTB" ] || { echo "ERROR: $GUEST_DTB not found. Run 'make guest' first."; exit 1; }

# Optional initramfs loader (M3.4). Built as a shell variable so the qemu line
# stays a single exec; empty when LINUX_INITRD is unset.
INITRD_LOADER=""
if [ -n "${LINUX_INITRD:-}" ]; then
  [ -f "$LINUX_INITRD" ] || { echo "ERROR: LINUX_INITRD=$LINUX_INITRD not found."; exit 1; }
  INITRD_LOADER="-device loader,file=${LINUX_INITRD},addr=0x4C000000"
fi

exec qemu-system-aarch64 \
  -machine virt,virtualization=on,gic-version=3 \
  -cpu cortex-a72 -smp 1 -m 1G \
  -nographic -serial mon:stdio \
  -kernel build/hypervisor.elf \
  -device loader,file="${LINUX_IMAGE}",addr=0x48080000 \
  -device loader,file="${GUEST_DTB}",addr=0x4A000000 \
  ${INITRD_LOADER} \
  ${QEMU_EXTRA_ARGS:-}
```

Note: `${INITRD_LOADER}` is intentionally unquoted so it expands to either nothing or the three-token loader spec; this is safe because the path is the only field that could contain spaces and it is captured inside the variable without further word-splitting concerns for typical paths. If the initramfs path may contain spaces, place it somewhere without spaces (standard for bring-up).

### Task 2: Add `/chosen` initrd properties to `guest/qemu_virt.dts`

**Files:**
- Modify: `guest/qemu_virt.dts`

The kernel reads the initrd location from `/chosen/linux,initrd-start` and `/chosen/linux,initrd-end` (guest IPA). We use a **generously-sized fixed reservation that the kernel trims**: `linux,initrd-end` is set to `start + 16 MB` (`0x45000000`). This is the cleanest of the three options:

- **Fixed reservation (CHOSEN):** `end = 0x44000000 + 0x01000000 = 0x45000000`. The kernel only *reads* the cpio stream until it ends; the `initrd-end` is an upper bound. Modern arm64 Linux handles `initrd-end` overshooting the real payload (it stops at the cpio TRAILER record). This keeps the `.dts` static and decoupled from the exact initramfs file size — no rebuild of the DTB when the busybox image changes size (as long as it stays under 16 MB). **Justification:** the `.dts` is a checked-in artifact compiled once by `make guest`; coupling its content to a user-supplied file's byte length (option B) would force a DTB rebuild per initramfs and add a build-time size computation with no real benefit. User-set (option C) pushes complexity onto every run. The fixed 16 MB reservation matches the 16 MB headroom pinned in the address map and is the simplest robust choice.
- (Rejected) **Build-time computed end:** compute `end = start + $(stat -c%s initrd)` in the Makefile and patch the DTB. More moving parts, requires the initramfs present at DTB-build time, and the kernel doesn't need the exact end.
- (Rejected) **User-set:** another env var per run; error-prone.

**Encoding:** root has `#address-cells = <2>` / `#size-cells = <2>`, but `/chosen/linux,initrd-start` and `linux,initrd-end` are **not** `reg`-style address/size pairs — by Linux convention they are **plain scalar cells** whose width the kernel auto-detects: a property of length 4 is read as a u32, length 8 as a u64 (`of_get_flat_dt_prop` → `early_init_dt_check_for_initrd`). For our addresses (`0x44000000`, `0x45000000`) a single u32 cell each is correct and unambiguous (they fit in 32 bits). The DTS syntax `<0x44000000>` emits exactly one 4-byte cell. We use the u32 form. (A u64 form `<0x0 0x44000000>` would also work but is unnecessary for sub-4 GB addresses; the u32 form matches the dominant convention seen in QEMU-generated and kernel-test DTBs.)

### Task 3: Confirm/select the console for the interactive shell (bootargs)

**Files:**
- Modify: `guest/qemu_virt.dts` (only if the M3.3 console handoff requires it — see decision below)

**Console decision (justified):**

There are two candidate consoles at this point:
- `ttyAMA0` — the M3.0 passed-through physical PL011 at IPA `0x09000000`. Always present; writes go straight to hardware (interleaved with hv output, accepted for bring-up). Requires **no** trap-emulation.
- `hvc0` — the M3.3 virtio-console. Present only if M3.3 landed; depends on the M3.1 MMIO bus + M3.2 vGIC IRQ injection working end-to-end.

**Recommendation for the M3.4 DoD: run the interactive shell on `console=ttyAMA0` (the PL011 passthrough), keeping `earlycon=pl011` for early logs.** Rationale:

1. **Lowest dependency surface for the headline DoD.** The PL011 path has worked since M3.0 and needs no vGIC/virtio correctness. Pinning the shell to `ttyAMA0` means the interactive-shell milestone does not silently regress if a virtio-console edge case is unstable — it isolates "boot to shell" from "virtio-console works".
2. **`earlycon` → `console` continuity.** `earlycon=pl011,0x9000000` brings up the early boot log; `console=ttyAMA0` makes the same UART the preferred `/dev/console`, so getty/`/init`'s shell lands on the device the operator is already watching. There is no handoff gap.
3. **The `/init` must match.** The shell only appears if the initramfs `/init` exec's a shell on the controlling terminal that the kernel made `/dev/console`. With `console=ttyAMA0`, the kernel opens `/dev/console` on the PL011; a standard `/init` that runs `exec /bin/sh` (or `setsid ... </dev/console >/dev/console 2>&1`) lands the prompt there. This is documented in Task 4's recipe so the two stay consistent.

If M3.3's virtio-console is fully working and you instead want the shell on `hvc0`, the change is: `bootargs = "earlycon=pl011,0x9000000 console=hvc0 nokaslr"` **and** the `/init` must direct the shell at `/dev/hvc0`. Keep `earlycon=pl011` regardless, because virtio-console is not available during early boot. This plan keeps `ttyAMA0` as the DoD console; the `hvc0` variant is documented as an option in Task 4.

- [ ] **Step 1: Create `docs/guest-initramfs.md`**

```markdown
# Guest initramfs (user-supplied) — busybox rootfs for M3.4

The M3.4 "boot to shell" milestone needs a small root filesystem. Like the
kernel `Image`, the initramfs is **supplied by you, not built in this repo**.
This doc is a reference recipe for producing a `cpio.gz` initramfs containing a
static busybox and an `/init` that drops to an interactive shell on the guest
console.

## What the hypervisor expects

- A gzip-compressed cpio (newc format) archive — a standard Linux initramfs.
- Loaded by QEMU at **physical** address `0x4C000000` via
  `-device loader,file=<initramfs>,addr=0x4C000000` (set `LINUX_INITRD`).
- Advertised to the kernel by the guest DTB `/chosen`:
  `linux,initrd-start = <0x44000000>` and `linux,initrd-end = <0x45000000>`
  (guest IPA; PA = IPA + 0x08000000). Keep the payload under 16 MB.
- The kernel unpacks it as the rootfs and runs `/init`.

## Address sanity

| Artifact | Guest IPA | Physical (QEMU `addr=`) |
|---|---|---|
| initramfs | `0x44000000` | `0x4C000000` |

64 MB above guest RAM base (`0x40000000` / PA `0x48000000`); 32 MB above the
DTB; clear of the kernel at IPA `0x40080000`.

## Recipe (host tools — needs a static busybox binary)

You need a statically-linked arm64 `busybox`. Either download a prebuilt
static aarch64 busybox, or build it:

```sh
# (optional) build a static arm64 busybox
git clone --depth=1 https://git.busybox.net/busybox
cd busybox
make ARCH=arm64 CROSS_COMPILE=aarch64-none-linux-gnu- defconfig
# enable "Build static binary (no shared libs)" in: make menuconfig
make ARCH=arm64 CROSS_COMPILE=aarch64-none-linux-gnu- -j"$(nproc)"
# -> ./busybox  (static aarch64 ELF)
cd ..
```

Assemble the initramfs tree:

```sh
mkdir -p initramfs/{bin,sbin,proc,sys,dev,etc}
cp busybox/busybox initramfs/bin/busybox
( cd initramfs && ln -sf busybox bin/sh )

cat > initramfs/init <<'EOF'
#!/bin/sh
mount -t proc     none /proc
mount -t sysfs    none /sys
mount -t devtmpfs none /dev 2>/dev/null || \
  /bin/busybox mdev -s
echo
echo "=== M3.4: busybox rootfs up — interactive shell ==="
# console=ttyAMA0 makes the PL011 the controlling /dev/console.
exec /bin/sh
EOF
chmod +x initramfs/init

# install the busybox applet symlinks at boot via the init above (mdev/ln),
# or pre-create the common ones:
for a in mount umount ls cat echo sh mdev cpio; do
  ln -sf busybox initramfs/bin/$a
done
```

Pack it into a `cpio.gz`:

```sh
( cd initramfs && find . | cpio -o -H newc | gzip -9 ) > initramfs.cpio.gz
ls -l initramfs.cpio.gz   # should be well under 16 MB
```

## Run

```sh
LINUX_IMAGE=/path/to/Image \
LINUX_INITRD=/path/to/initramfs.cpio.gz \
make run
```

Expected: after the M3.0–M3.3 boot, the kernel logs
`Unpacking initramfs...`, runs `/init`, prints the banner, and an interactive
busybox prompt appears:

```
=== M3.4: busybox rootfs up — interactive shell ===
/ #
```

Type `ls /` or `cat /proc/cpuinfo` and see output — that is the M3.4 DoD.

This repo's `guest/qemu_virt.dts` sets `console=ttyAMA0` (the passed-through
PL011), so the shell runs on `ttyAMA0` and `/init`'s `exec /bin/sh` lands on

    exec setsid sh -c 'exec sh </dev/hvc0 >/dev/hvc0 2>&1'

Keep `earlycon=pl011` either way — virtio-console is not available during early
boot.
```
