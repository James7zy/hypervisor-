## 问题陈述

一次 grilling 会话对本仓库提出了"下一步做什么才合理"的问题，并明确要求**不依赖既有路线图**来思考。会话通过读代码（而非读文档）审计现状，产出了 12 个决策问题。

这些问题的结论已被压缩进设计文档的一张汇总表，每条一句话。**但压缩丢掉了最有价值的部分**：每个问题当时有哪些备选、为什么否决其余、以及结论依赖哪些前提。

在"学习深度"这一既定目标下，这个损失尤其严重——**推理过程本身就是要保留的产物**。一份只有结论的清单，半年后无法回答"当时为什么不这么做"，也无法在前提变化时判断哪条结论该跟着变。

此外，权属信息若不留档，这 11 条代定结论会随时间被误记为"经过深思熟虑的共同决定"。

## 解决方案

以 12 个问题为骨架，逐条留档：**问题 → 备选 → 结论 → 权属 → 理由 → 反方论点 → 推翻条件**。

关键设计：每条都带一个**推翻条件**——一句可证伪的陈述，说明"如果这件事成立，这条结论应当被重新审视"。这让本文成为一份可执行的重访清单，而不是一篇追忆。

## Q1 — 首要目标：学习深度，还是 ACRN 终态？ 【用户】

**备选：** (a) 学习 EL2 核心机制；(b) 尽快跑通 ACRN 模型这个系统。

**结论：(a) 学习深度。** 这是全表唯一由用户直接给出的答案。

**理由：** 两者指向不同方向。若为学习，剩余最密集的内容是上下文切换 + 调度，且它是**唯一**尚未触碰的真正 ARM 架构难点——之后的 M12–M14 大多是 ABI 管道、内核模块和用户态 C，在哪个项目里都能学到。若为系统落地，则应更早开始 hypercall/HSM/DM 链条，因为那是最长、最不确定的一段，且不严格需要抢占才能演示。

**为何这个问题必须排在第一：** 它是整棵决策树的根。Q7、Q8、Q9、Q12 的结论**直接由它推导**，Q3 的力度也受它影响。会话中 Q7 正是在此答案给出后被反转的。

**推翻条件：** 若目标转向"尽快拿到可演示的 ACRN 模型"，**立即重访 Q7、Q8、Q9、Q12**——这四条在工程吞吐目标下会得出不同结论。

## Q2 — `CPU_OFF` 缺陷：是被推迟的 bug，还是第一切片？ 【代定】

**背景：** CLAUDE.md 以"M11 反正要重写这块状态管理"为由推迟了 `CPU_OFF` 干掉整个 VM 的缺陷。本问题检验这个理由是否成立。

**备选：** (a) 作为调度器工作的第一切片；(b) 作为独立 bug 先修；(c) 继续推迟。

**结论：(a)。**

**理由：** `psci_power_down()` 使用**每 VM** 的 `off` 标志，**正是因为**每 vCPU 运行状态不存在。而每 vCPU 运行状态（`OFF`/`RUNNING`/`BLOCKED`）恰好是调度器需要的第一个数据结构。**这不是两件事，是同一件事。** 原推迟理由（"M11 反正要重写"）其实无意中说对了——但结论下反了：正因为 M11 要建这个结构，这个 bug 才应该**由 M11 的第一切片顺带修掉**，而不是继续挂着。

**附加收益：** 它自带一个现成的手工复现路径（`echo 0 > /sys/devices/system/cpu/cpu1/online`），可直接转化为验收断言。

**否决 (b) 的理由：** 独立修会先造出一套只为这个 bug 服务的临时状态表示，随后又被切片 S2 推翻——白做一遍。

**推翻条件：** 若发现每 vCPU 状态机的设计能与 PSCI 语义解耦（即 `CPU_OFF` 可以不引入运行状态就正确实现），则本条前提失效，退回 (b)。

## Q3 — 加抢占前，是否先建"上下文切换正确性"探测装置？ 【代定】

**备选：** (a) 先写 `svm5`：盖章每个 EL1 系统寄存器、让出、校验；(b) 靠启动两个 Linux 观察损坏；(c) 直接写调度器，出问题再说。

**结论：(a)。**

**理由：** 子代理审计确认，**没有任何自动化测试启动 Linux**，五个场景全是裸机 SVM 客户机，且这些客户机几乎不碰 EL1 状态。因此今天没有任何东西能发现一个丢失的 EL1 寄存器。在这个前提下加调度器，等于要靠二分寄存器列表来调 Linux 内存损坏。

**核心原则：先写探测器，再写被探测的东西。** 一个会盖章并校验 EL1 状态的 `svm5`，把"我是不是漏了个寄存器？"从一整夜的排查变成一行测试失败，且几秒跑完，不必等 25 秒的 Linux 启动。

**否决 (b) 的理由：** 25 秒以上、不确定，而且一个被损坏的 `TTBR0_EL1` 表现为不透明的内核 panic，而不是一个寄存器名。作为集成门禁有价值（见 Q7/S8），作为探测器无用。

**推翻条件：** 若 `svm5` 的实现成本被证明远超预期（例如需要新的构建机制而非仅一个 `HV_GUEST` profile），重新评估——但即便如此，正确做法是简化探测器，而不是取消它。

## Q4 — 首个调度目标：2 VM × 2 vCPU 跑 2 pCPU，还是更小？ 【代定】

**背景：** 路线图给 M11 定的目标同时改变三件事：上下文切换完整性、调度策略、跨 pCPU 迁移。

**备选：** (a) 同一 VM 的 2 vCPU 跑 1 pCPU；(b) 不同 VM 的 2 vCPU 跑 1 pCPU；(c) 直接上完整 2×2。

**结论：(a) 然后 (b)，两个切片，全程不含迁移。**

**理由：** **它们是两个切片，不是两个选项。** (a) 共享 Stage-2 和 VMID，因此不涉及 VMID/TLB 切换——任何失败**必然**出在 EL1 或 vGIC 状态上。(b) 只增加一个新变量（`VTTBR_EL2` 切换 + TLB 失效纪律），而那正是真正微妙的 ARM bug 藏身之处。

**核心原则：在虚拟化里永远不要一次改两个变量。**

**迁移被单独剔除：** 迁移是第四个切片，不属于本里程碑。把它折叠进来会让一个本来在讲状态保存的切片同时在讲位置无关性。

**推翻条件：** 若 (a) 一次通过且毫无意外，可考虑把 (b) 与 S5（`CNTVOFF`）合并以节省一轮迭代——但只在 (a) **确实**零意外时。

## Q5 — FP/SIMD 放在哪？ 【代定】

**备选：** (a) 第一个切换切片就急切保存；(b) `CPTR_EL2.TFP` 陷入，惰性保存；(c) 完全推后，初期只跑不用 FP 的客户机。

**结论：(c) 先，然后 (a)；(b) 明确推迟为优化。**

**理由：** 切片 1 应在 FP 明确排除的前提下验证 EL1 系统寄存器 + vGIC 切换（现有 SVM 客户机不用 FP），这样失败**只有一个可能原因**。然后把 FP 作为独立切片急切实现，配自己的测试。

**否决 (b) 作为首选的理由：** 惰性 FP 是**优化**，不是正确性方案。在急切版本跑通前做它，等于同时调一个正确性 bug 和一个惰性 bug。(b) 确实是真实 hypervisor 的答案，也值得学——但顺序错了就学不到，只会陷在混合症状里。

**对既有不变量的澄清：** 路线图称 M11"解除 `-mgeneral-regs-only` 的不保存假设"，这个措辞暗示缺口是 FP/SIMD。**不是。** FP/SIMD 是八切片中的第六个，而该不变量本身（EL2 从不发射 FP 指令）**依然正确，应当保留**——它约束的是 hypervisor 自身，与是否保存客户机 FP 状态无关。

**推翻条件：** 若客户机负载在 S6 之前就需要 FP（例如为验收引入的测试负载），S6 需前移——但仍应急切实现，不跳到 (b)。

## Q6 — 既有的 vuart/`g_vgicd` 竞争：现在修，还是并入调度器？ 【代定】

**备选：** (a) 现在作为独立小切片修掉；(b) 并入调度器工作；(c) 不管，很少见且从未发作。

**结论：(a)，立刻，排在清单最前。**

**理由：** 与 Q2 的 `CPU_OFF` 不同，这些**不是**调度器会强迫你重做的工作——它们是**今天就独立错误**的 bug。子代理审计确认：vuart RX 环由 pCPU0 生产、属主 pCPU 消费，字段无锁且非 `volatile`，`ris` 是跨核非原子读改写；`g_vgicd[vmid]` 被同 VM 两个 vCPU 共享且无锁。`spinlock.h` 记录的"每核私有"前提**在 M10 引入跨 pCPU 控制台路由时就已失效**，注释至今未更新。

**决定性论点：** 抢占会把每个竞争窗口从纳秒拉宽到毫秒，且 vCPU 可能在 MMIO 模拟中途被换出。**如果放到加抢占之后再修，每个奇怪的调度器症状都会有两个候选病因。** 先把桌面清干净。

**否决 (c) 的理由：** "从未观察到"不是不存在的证据——尤其对一个只在人类打字速度下才有机会触发的竞争而言。而你正要大幅改变时序。

**已知薄弱点：** S0 的验证本身是本里程碑**唯一真正困难的测试问题**（详见设计文档"测试决策"）。现有接缝无法可靠复现纳秒级窗口。这一点已被显式记录而非粉饰。

**推翻条件：** 若竞争分析被证明有误（例如 vuart 消费端实际上也总在 pCPU0），本条降级为注释订正。**应在 S0 动工前用一次定向复核确认，而不是直接开写。**

## Q7 — 缺失的自动化 Linux 启动门禁，是不是最高优先项？ 【代定，会话中被反转】

**备选：** (a) 是，先于一切新功能；(b) 否，ADR-0009 有意选择手工验证；(c) 折中，自动化但放在独立 `make test-linux` 目标。

**首次结论（Q1 回答之前）：(c)，且优先级很高。**

**修订结论（Q1 回答之后）：(c) 的形式保留，但优先级降至最后（S8）。** ⚑

**反转理由：** ADR-0009 的推理在**系统还小、只有一个人跑**时是成立的；如今 4577 行 hypervisor、双 VM、SMP，"客户机还能启动"已成为最有价值却未做的断言。**但用户明确目标是学习深度后，性价比变了**：自动化 Linux 门禁保护的是**已学完的东西不退化**——那是工程价值，不是学习价值。且已手工验证两次（M8、M9），地基没有脆到必须先加固。

**这是整场会话中唯一一次立场反转，因此最值得怀疑。**

**已知代价（必须记录）：** Q2 的 `CPU_OFF` 修复有一个完美断言（`echo 0 > .../cpu1/online` 后 CPU0 仍在运行），但**它需要 Linux 客户机**。S8 推迟意味着 **S2 的自动化覆盖只能退到 SVM 级别的等价物**。这是本次降级的直接成本，不是可忽略的细节。

**阻塞子问题：** `LINUX_RUN.sh` 写死了开发机本地绝对路径。任何自动化门禁都先需要一个可复现镜像，而这是未决决策：入库裁剪 Image、脚本化内核构建、还是文档化下载。**应在 S8 排期前解决。**

**推翻条件（两条，任一成立即重访）：**
1. 目标从学习深度转向工程吞吐（见 Q1）；
2. **在 S0–S7 任一阶段发生一次"改动破坏 Linux 启动但 `make test` 全绿"的事件**——一次即足以证明降级判断错误。

## Q8 — Q1 的答案是否改变 Q6/Q7 的取舍？ 【代定】

**备选：** (a) 两个都保留为前置；(b) 只保留 Q6，砍掉 Q7；(c) 两个都砍，直接进上下文切换。

**结论：(b)。**

**理由：** 这个问题存在的意义，是**逼自己承认第一轮的建议默认了"工程稳健"而非用户实际声明的"学习深度"**。Q6 和 Q7 都是纯工程卫生，都不教授 EL2 知识。诚实的反方论点是："这两件事都在拖延真正的学习内容。"

**保留 Q6 的正当性来自学习效率，而非代码质量** ——这个区分很重要：如果理由是"代码应该干净"，在学习深度目标下它就该被砍掉。

**推翻条件：** 同 Q7 的两条推翻条件。

## Q9 — "学习深度"的操作定义：跑通，还是能重新推导？ 【代定】

**备选：** (a) 功能导向——写对、跑通、下一步；(b) 机制导向——每个寄存器都能回答"为什么必须切换、不切换的具体后果是什么"，并**故意制造一次失败**验证理解；(c) 规范导向——对着 ARM ARM D 章逐条核对求完整。

**结论：(b) 为主，(c) 兜底。** ⚑

**理由：** 这是 Q1 带来的最大改变。若目标是学习，**故意让它坏**是最高效手段。具体做法：`svm5` 建好后，**先只保存一半寄存器**，观察它怎么死、失败模式长什么样，记入 `docs/debug/`，再补全。这比一次写对学到的多得多。

**依据用户既有习惯：** 仓库已有 `docs/debug/` 目录（6 篇调试走查，其中 4 篇中文），说明用户本来就靠这种方式学习。本决策是顺着既有习惯，而非强加方法论。

**否决纯 (c) 的理由：** 逐条核对规范会给你一张**背下来的清单**，而不是理解。清单会忘，"我见过 `TTBR0_EL1` 没存时客户机是怎么死的"不会。

**(c) 的保留位置：** 作为补全阶段的兜底核对，确保没有既没推导出、也没被测试暴露的遗漏。

**推翻条件：** 若"故意半实现"在实践中产生的失败模式过于混沌（多个寄存器同时缺失导致症状无法归因），改为**一次只遗漏一个寄存器**的受控实验。

## Q10 — EL1 系统寄存器 save/restore 写在汇编还是 C？ 【代定】

**背景：** 现有 `vmexit_asm.S`（213 行）和 `irq_handler_asm.S`（94 行）已在汇编中保存 GPR 和 `SP_EL1`。新增约 25 个 EL1 系统寄存器放哪？

**备选：** (a) 全部塞进现有汇编路径；(b) 汇编只保存最小必需集，EL1 批量 save/restore 用 C 写成独立函数，仅在真正切换 vCPU 时调用；(c) 全部用 C，汇编只做跳板。

**结论：(b)。**

**理由：** 这不只是工程选择，也是**学习上正确的划分**——它强迫回答一个核心问题：**"哪些状态是每次异常都必须保存的，哪些只在换 vCPU 时才需要？"** 这个区分正是 KVM 和 Xvisor 的核心设计点，且性能影响巨大：每次 MMIO trap 都存 25 个系统寄存器是灾难。

**否决 (a) 的理由：** 会让你**错过这个洞察**，并让 `vmexit_asm.S` 膨胀到难以维护。

**接口设计要求：** 切换接口应是**单一窄入口点**（接受目标 vCPU），把换出方的 save/restore 作为内部实现。调用者（S3 的 `WFI` trap 处理器、S7 的定时器 tick）不应需要知道寄存器清单存在。**抵制把 `save`/`restore` 作为公开配对暴露**——那会诱导调用者以错误顺序编排。

**应产出 ADR：** 这条"两层状态划分"是本里程碑的核心设计决策，直接决定 trap 开销，应在实现切片时记录为 ADR。

**推翻条件：** 若剖析显示 C 函数调用开销在切换路径上不可接受（在协作式切换下极不可能），再考虑把热路径下沉到汇编——但保留两层划分本身。

## Q11 — 第一个切片的切换触发点：协作式还是抢占式？ 【代定】

**备选：** (a) 协作式——只在客户机 `WFI`/`WFE` 时切换（`HCR_EL2.TWI/TWE` 陷入）；(b) 时间片抢占——EL2 物理定时器周期触发；(c) 先 (a) 后 (b)。

**结论：(c)，且 (a) 这一步比表面看起来重要得多。**

**理由：** 协作式切换让你在**完全可控的时机**验证 save/restore 正确性——切换点是确定的、可复现的、可打印的。而抢占式切换发生在任意指令边界，一个漏存的寄存器可能几百万次切换才暴露一次。

**核心原则：先在确定性环境里把状态机做对，再引入非确定性。**

**(a) 不是为了简单而走的弯路：** `WFI` 陷入本身就是必学内容——真实 hypervisor 靠它做空闲 vCPU 让出。它是要学的东西，不是通往抢占的临时脚手架。

**应产出 ADR：** "协作式先于抢占式"及以 `WFI` trap 作为让出点，应记录为 ADR。

**推翻条件：** 若客户机在测试场景中根本不发 `WFI`（裸机 SVM 客户机需显式加入），则需要为 `svm5` 显式构造让出点——这是实现细节，不改变结论。

## Q12 — 动手前先读参考实现吗？ 【代定】

**背景：** CLAUDE.md 明确要求"设计任何新子系统前先查现有实现"，且 `../xvisor`、`../bao-hypervisor`、`../acrn-hypervisor` 就在旁边。但对学习目标而言，先读会削弱自己推导的价值。

**备选：** (a) 先自己推导清单和切换时机，写完第一版，**然后**对照找差异；(b) 先读 xvisor 的 ARM64 上下文切换，照着做；(c) 完全不读，纯靠 ARM ARM。

**结论：(a)，带逃生舱。** ⚑

**理由：** 直接来自 Q1 与 Q9(b)。先读会给你一份正确答案，但会**跳过推导过程**——而推导正是想要的东西。自己列一遍清单、跑 `svm5`、发现漏了什么、再去对照 bao（它最小最干净，适合对照）——你会记住每一个漏掉的寄存器，以及漏掉它的**具体症状**。这与 Q9 的"故意制造失败"是同一个策略的两面。

**与 CLAUDE.md 既有指示的关系：** CLAUDE.md 的"先查现有实现"是为**避免重复造轮子和踩已知坑**而设的工程规则。本条在学习深度目标下**有意偏离**它，并非否定该规则——偏离范围严格限定在"上下文切换寄存器清单"这一个子问题上，其余子系统仍应先查。**这个偏离必须显式记录，否则会被误读为违反项目指示。**

**逃生舱：** 若卡住超过一天，读，不要硬扛。学习价值来自"推导 → 验证 → 对照"的完整循环，不来自受苦本身。

**推翻条件：** 目标转向工程吞吐时立即失效——那时应先读，直接采用经过验证的清单。
