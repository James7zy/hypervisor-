## 问题陈述

路线图把 M11 描述为"增加 vCPU 调度器"并"解除 `-mgeneral-regs-only` 的不保存假设"。代码审计表明，这个说法把差距**说轻了很多**。

**这个代码库里根本没有 vCPU 上下文切换。** 不是不完整——是不存在：

- `struct vcpu` 里有通用寄存器、`SP_EL1`、`ELR/SPSR_EL2`、`HCR_EL2`、`VTTBR_EL2` 和四个 vGIC 寄存器。**零个 EL1 系统寄存器。** 全树搜索找不到对以下寄存器的任何保存、恢复、读或写：`SCTLR_EL1`、`TTBR0_EL1`、`TTBR1_EL1`、`TCR_EL1`、`MAIR_EL1`、`AMAIR_EL1`、`VBAR_EL1`、`CPACR_EL1`、`TPIDR_EL0`、`TPIDRRO_EL0`、`TPIDR_EL1`、`CONTEXTIDR_EL1`、`ESR_EL1`、`FAR_EL1`、`PAR_EL1`、`SP_EL0`、`CSSELR_EL1`、`AFSR0/1_EL1`、`ELR_EL1`、`SPSR_EL1`、AArch32 banked SPSR、`MDSCR_EL1`、`ACTLR_EL1`。
- `vgic_save()` 在整个代码树中**零调用者**。它自己写于 M2 的注释说："M2.5 的 timer 上下文切换是第一个使用者。"那件事从未发生；这个函数作为死代码横跨了九个里程碑。
- `CNTVOFF_EL2` 只在两处被写成字面量常数 `0`，并且不是 per-vCPU 字段。

**今天这样是"构造上正确"的**：在静态 1:1 vCPU↔pCPU 绑定下，一个 pCPU 永远只跑一个 vCPU，所以 EL1 状态就留在硬件里，从不需要换出。被保存的集合恰好就是 EL2 异常入口自身会破坏的那些。**但只要两个 vCPU 共享一个 pCPU，每一个未保存的寄存器都会变成静默的、不确定的客户机状态损坏**——虚拟化中最难诊断的一类 bug。

另有两个问题在绑定模式下完全不可见，但在引入抢占的瞬间就变成正确性 bug：

1. **`CNTVOFF_EL2 = 0`。** 一个被换出的 vCPU，物理计数器照样在走。客户机 Linux 用 `CNTVCT_EL0` 计算定时器 deadline；丢失一个时间片后醒来，会看到虚拟时间发生跳变，可能陷入定时器中断追赶的死循环。

2. **已经存在的跨 pCPU 数据竞争。** `spinlock.h` 记录的设计前提是"其余部分靠一次构建只读（Stage-2）或每核私有（vcpu/vGIC/timer）来保持无锁"。**这个前提在 M10 就已经不成立了**——那时引入了跨 pCPU 控制台路由和 2-vCPU VM。不变量注释过期了，代码从未跟上：

   - vuart 的 RX 环是真正跨核的：`vuart_rx()` 在 pCPU0 上推进 `rx_head`，而 `vuart_read()` 在属主 pCPU 上推进 `rx_tail`（当控制台焦点在 VM1 时，属主 pCPU 不是 pCPU0）。字段既没有锁，也不是 `volatile`。`ris` 是跨核的非原子 `|=`/`&=` 读改写。
   - `g_vgicd[vmid]` 被一个 VM 的两个 vCPU 共享，它们可以在不同 pCPU 上并发触发 MMIO trap。无锁。

   这些在人类打字速度下很少发生，这正是它们至今未被观察到的原因。**抢占会把上述每一个窗口从纳秒拉宽到毫秒**，而且 vCPU 现在可能在 MMIO 模拟中途被换出。

最后，一个相关缺口限定了以上工作能有多安全地推进：**没有任何自动化测试启动真正的 Linux 客户机。** `make test` 的五个场景全部使用裸机 SVM 客户机。Linux 启动、virtio-console、boot-to-shell 三项之间有约 4000 行 spec 和 plan，自动化覆盖为零；M8 和 M9 是手工验证的，用的是写死在开发机本地路径上的内核镜像。

## 解决方案

把 M11 当作**八个有序切片**，而不是一个里程碑。**先造探测器，再造被探测的东西**；在引入非确定性之前先清掉既有竞争；**每个切片只改变一个变量**。

排序由"学习深度"目标驱动：一个好切片的衡量标准不是"多快能跑出可用调度器"，而是"这个切片失败时，多快能告诉我是哪个寄存器、或哪个机制我理解错了"。

| 切片 | 交付物 |
|---|---|
| **S0** | 修复既有的 vuart / `g_vgicd` 跨 pCPU 竞争；订正 `spinlock.h` 过期的不变量注释 |
| **S1** | `svm5` EL1 状态探测客户机 + `run_svm5_test.sh`——**预期一落地就失败** |
| **S2** | per-vCPU 运行状态机；`CPU_OFF` 只停调用者所在的 vCPU |
| **S3** | 协作式上下文切换，同 VM，2 vCPU 跑 1 pCPU——`svm5` 转绿 |
| **S4** | 跨 VM 切换：`VTTBR_EL2`/VMID 切换 + TLB 纪律 |
| **S5** | per-vCPU `CNTVOFF_EL2` |
| **S6** | FP/SIMD 急切保存/恢复 |
| **S7** | 抢占式时间片 |
| **S8** | 自动化 Linux 启动门禁（`make test-linux`），从 S0 位置推迟至此 ⚑ |

**头条可观测目标：M10 的两个 2-vCPU VM 在 2 个 pCPU 上时间片轮转**，两个客户机都到达交互式 shell，且两个 VM 中并发运行的 FP 负载结果无损坏。

### 为什么这不是一个里程碑

路线图把 M11 当作单一工作单元。审计显示它至少包含三个独立的风险面——既有并发 bug、缺失的架构状态、缺失的检测能力——它们以不同方式失败，用不同工具调试。把它们排成切片、每片只改一个变量，才能让失败是**可归因的**。前两个切片根本不是调度器工作；它们是让调度器工作**可学**而不仅仅是**可挺过去**的前置条件。

4. 作为 hypervisor 开发者，我希望有一个裸机客户机为每个 EL1 系统寄存器写入特征值，这样我就拥有"上下文切换必须保住什么"的基准真相。

### 将构建或修改的模块

- **`struct vcpu`** 增加一个 EL1 系统寄存器块、一个运行状态枚举、一个 per-vCPU `CNTVOFF_EL2`，以及（S6 时）一个 FP/SIMD 块。所有字段追加在汇编可见前缀之后；`check_offsets` 相应增加条目。
- **一个新的上下文切换模块**，拥有 `vcpu_save_el1_state()` / `vcpu_restore_el1_state()` 和切换入口点。**这才是本里程碑真正的主题**；它应当是一个"深模块"——用一个窄接口（`switch_to(vcpu)`）覆盖架构状态的全部广度。
- **`struct vuart`** 增加锁；环形缓冲区字段获得正确的顺序语义。**vGIC MMIO 模拟状态**增加锁。**`spinlock.h`** 的前提注释被订正。
- **PSCI** 获得每 vCPU 的下电语义；`psci_power_down()` 拆分，使 `CPU_OFF` 与 `SYSTEM_OFF`/`SYSTEM_RESET` 不再共用同一路径。
- **vGIC** 获得 `vgic_save()` 的第一个真实调用点，与既有的 `vgic_restore()` 配对。
- **vtimer** 把 `CNTVOFF_EL2` 从"两处写死的常数"变为 per-vCPU 状态；secondary 路径中重复的内联初始化折回共享初始化。
- **异常入口汇编**：**不**扩充 EL1 寄存器集合。

### 值得记 ADR 的架构决策

这里有三个决策属于本项目历来会记录的那一类，各自应在实现它的切片上产出一份 ADR：

- **两层状态划分**——哪些寄存器每次异常保存、哪些每次切换才保存。这是本里程碑的核心设计决策，直接决定 trap 开销。
- **协作式先于抢占式切换**，以及以 `WFI` trap 作为让出点。
- **急切先于惰性 FP/SIMD**，明确推迟 `CPTR_EL2.TFP`。

另需注意：**ADR-0002**（"单一全局 VM、单 vCPU"）与 **ADR-0009**（"无 CI、手工验证"）都被本工作部分取代；尤其 ADR-0009 应在 S8 时被**显式重访**，而不是被悄悄违背。

### 接口

切换接口应当是**单一窄入口点**，接受目标 vCPU，把换出方的 save/restore 作为其内部实现。调用者（S3 的 `WFI` trap 处理器、S7 的定时器 tick）不应需要知道寄存器清单的存在。**抵制把 `save`/`restore` 作为公开配对暴露出去**——那会诱导调用者以错误顺序编排它们。

## 测试决策

### 什么是这里的好测试

好测试**只观察客户机能观察到的东西**。本里程碑必须捕获的失败模式是"**硬件会破坏、但没人列进清单的那个寄存器**"——任何针对实现的测试都找不到它，因为实现里的寄存器清单**本身就是 bug**。只有一个"写状态 → 让出 → 读回"的客户机才能检测遗漏。相应地，一个断言 `vcpu_save_el1_state()` 写入了某个特定结构体字段的测试，是在拿清单验证清单自己，会在系统已损坏时照样通过。

### 主接缝：`svm5`，一个裸机 EL1 状态探测客户机

**一条接缝，完全沿用既有先例。** 已有五个场景是同样形状（`run_svm_test.sh` 到 `run_shell_test.sh`）：构建客户机 `.bin`、在 QEMU 下启动、对串口输出做 `grep -qF` 固定字符串匹配。`svm5` 增加第六个 `HV_GUEST` profile 和一个脚本；无新测试框架，无新构建机制。

行为：为每个 EL1 系统寄存器写入按寄存器区分的特征值，让出（`WFI`），恢复后逐个校验，为任何失败的寄存器打印一行**指名**输出。测试断言成功字符串存在、且不出现失配标记——这正是 `run_shell_test.sh` 已在使用的"存在/不存在"断言模式。

**这个测试在刚写出来时预期就是失败的。** 那次失败就是 S1 的交付物：它证明探测器看得见这个 bug。按决策 #8，它还应当针对一份**故意不完整**的寄存器清单运行，并把观察到的失败模式记入 `docs/debug/`。

**已考虑并否决的替代方案：**
- **针对 save/restore 函数的 C 单元测试**——测的是实现，抓不到被遗漏的寄存器（见上）。
- **启动两个 Linux 客户机并观察损坏**——25 秒以上、不确定，而且一个被损坏的 `TTBR0_EL1` 表现为一次不透明的内核 panic，而不是一个寄存器名。作为集成门禁（S8）有价值，作为探测器无用。

### 各切片的额外覆盖

- **S0 需要一个竞争测试，而这是本里程碑唯一真正困难的测试问题**：现有场景无法可靠复现一个纳秒级窗口。可选方案是做一个压力场景——一边驱动控制台输入、一边让两个 VM 并发触发 GICD MMIO——或者接受 S0 采用基于评审的验证并依赖别处无回归。**这是测试计划中最薄弱的一点，应在实现时解决，而不是粉饰过去。**
- **S2 有现成断言**：`echo 0 > /sys/devices/system/cpu/cpu1/online` 之后 CPU0 必须仍在运行。目前是手工复现，应当自动化——但注意它需要一个 Linux 客户机，而那正是 S8 提供的东西。**若 S8 保持推迟，S2 的自动化覆盖就只限于一个 SVM 级别的等价物。**
- **S4 需要自己的断言**，因为 `svm5` 接缝只能看到单个客户机能看到的东西：两个 VM 各自在**同一个 IPA** 写入不同特征值，切换后校验隔离性。
- **S6** 为 `svm5` 扩充一个 FP/SIMD 盖章-校验块。
- **S7** 应断言两个 VM 中的**并发前进**，而不仅仅是"无损坏"。
- **`check_offsets`** 继续守护 asm/C 偏移漂移，并随 `struct vcpu` 增长而增加条目。

## 范围之外

- **vCPU 在 pCPU 之间的迁移。** 全程保持绑定。迁移是独立议题，折叠进来会违反"一次一个变量"原则。
- **经由 `CPTR_EL2.TFP` 的惰性 FP/SIMD。** 明确作为优化推迟。
- **超出 2×2-on-2 头条目标的 vCPU 超配。** 更高的超配比不是本里程碑目标。
- **任何超出简单轮转时间片的调度策略。** 优先级、公平性、实时保证都是后续议题。
- **Hypercall ABI、VM 生命周期、HSM、Device Model、virtio**——M12–M14。
- **RK3588 / 运行时 FDT 解析**——M15。
- **SMMU/DMA 隔离**——按既定路线图决策推迟。
- **调试/跟踪寄存器状态**（`MDSCR_EL1` 及断点/观察点组）中超出客户机可观测需求的部分。
- **AArch32 客户机支持。** AArch32 banked 寄存器为完整性起见列入"未保存"清单，但客户机仅限 AArch64。

## 补充说明

**关于路线图的表述。** 路线图 M11 条目说该里程碑"解除 `-mgeneral-regs-only` 的不保存假设"。这个措辞暗示缺口是 FP/SIMD。**它不是**——FP/SIMD 是八个切片中的第六个，而该不变量本身（EL2 从不发射 FP 指令）**依然正确，应当保留**。真正的缺口是 vCPU 上下文切换不存在。

**关于 ⚑ 标记。** 三个决策基于"学习深度"得出结论，在"工程吞吐"目标下会得出不同结论：推迟 Linux 门禁（7）、故意先交付不完整的寄存器清单（8）、延后阅读参考实现（11）。**若目标改变，先重访这三条。** 尤其决策 7 是在 grilling 中途被反转的——它最有可能值得再次反转。

**关于 S0 与学习目标。** S0 是纯工程卫生，不教授任何 EL2 机制；一个站得住脚的反方论点是它推迟了真正的学习内容。保留它的理由是：**调试一个同时存在已知竞争和未知上下文切换 bug 的系统，花在排除干扰上的时间会超过花在理解 ARM 状态上的时间**——正当性来自学习**效率**，而不是代码质量。

**关于 S8 中被阻塞的子问题。** `LINUX_RUN.sh` 写死了一个指向内核镜像的开发机本地绝对路径。任何自动化 Linux 门禁都首先需要一个可复现的镜像，而那是一个未决决策：入库一个裁剪过的 Image、脚本化内核构建，还是文档化一个下载步骤。应在 S8 排期之前解决。

**关于内存约束。** 内核 Image 地址预算（约 31 MB，见 CLAUDE.md）和 `-m 4G` 要求不受本里程碑影响，但会约束 S8 的镜像选择。
