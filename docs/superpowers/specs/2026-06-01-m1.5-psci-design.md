# Hypervisor — M1.5 (PSCI) Design

- **Date**: 2026-06-01
- **Project**: `hypervisor-`
- **Milestone**: M1.5 — PSCI
- **Target platform**: QEMU `virt` (AArch64)
- **Status**: Design approved, ready for implementation planning

> Split out of the original combined M2 spec (now superseded). PSCI is independent
> of the interrupt path — it rides M1's existing HVC dispatch and touches no GIC,
> timer, or new exception path — so it lands first as a low-risk confidence win.

---

## 1. Purpose & Positioning

M1.5 adds a minimal **PSCI** (Power State Coordination Interface) responder reachable
over HVC. It is the smallest useful slice on top of M1: no new hardware, no new
exception path, one new file plus a dispatch hook in the existing HVC handler.

It exists as its own milestone because it is completely orthogonal to the vGIC work
(M2) and the timer work (M2.5), and proving it first exercises the M1 HVC plumbing
end-to-end with near-zero risk.

### Roadmap context

| Milestone | Goal |
|---|---|
| M1 — Bare-Metal SVM *(done)* | Stage-2 MMU, single vCPU, EL1 SVM launch, HVC |
| **M1.5 — PSCI** *(this spec)* | PSCI VERSION/FEATURES/CPU_OFF/SYSTEM_OFF over HVC |
| M2 — vGIC software injection | virtual interrupt delivery, no physical hardware |
| M2.5 — Physical timer + GIC + HW-forwarding | real interrupt drives the vGIC |
| M3 — Linux Guest | boot Linux to shell; SMP via PSCI CPU_ON |

## 2. Scope

### 2.1 In scope

- PSCI dispatcher in `common/psci/`, called from `handle_hvc`.
- Functions: `VERSION` (returns PSCI 1.1 = `0x00010001`), `FEATURES`, `CPU_OFF`,
  `SYSTEM_OFF`, `SYSTEM_RESET`.
- SMCCC service-byte routing: `handle_hvc` sends function IDs whose top byte is
  `0x84` (SMC32) or `0xC4` (SMC64) to `psci_handle`.

### 2.2 Out of scope

- `CPU_ON` and SMP bring-up — present as a dispatch case returning `NOT_SUPPORTED`
  (M3 fills it in).
- `CPU_SUSPEND`, `MIGRATE`, `AFFINITY_INFO`, and the full DEN0022 surface.
- Any GIC, timer, or interrupt work (M2 / M2.5).

## 3. Architecture

PSCI shares the existing M1 HVC trap path; no new vector or asm:

```
guest: hvc #0   x0 = 0x84000000 (PSCI_VERSION)
  el1_sync_handler (vectors.S +0x400)  ── existing M1 path
    handle_exit → EC=0x16 → handle_hvc(regs)
      svc = x0 >> 24
      if svc == 0x84 || svc == 0xC4:  psci_handle(regs)   ── new
      else if x0 == HC_GUEST_DONE:     hv_restore()        ── existing M1
    el1_sync_handler eret-back path returns to guest with regs->x[0] = result
```

`psci_handle` writes the return value into `regs->x[0]`; the existing
`el1_sync_handler` eret-back path returns control to the guest after the HVC.

## 4. Component Design

`common/psci/psci.h` — function IDs and return codes. `common/psci/psci.c` —
`void psci_handle(struct vcpu_regs *regs)` switching on `regs->x[0]`:

| Function | ID | Behaviour |
|---|---|---|
| `VERSION` | `0x84000000` | `regs->x[0] = 0x00010001` |
| `FEATURES` | `0x8400000A` | `SUCCESS` for the implemented set, else `NOT_SUPPORTED` |
| `CPU_OFF` | `0x84000002` | print + `wfi` loop (single vCPU) |
| `SYSTEM_OFF` | `0x84000008` | print + `wfi` loop |
| `SYSTEM_RESET` | `0x84000009` | print + `wfi` loop |
| `CPU_ON` (32/64) | `0x84000003`/`0xC4000003` | `NOT_SUPPORTED` (M3) |
| default | — | `NOT_SUPPORTED` |

Build wiring: add `common/psci/psci.o` to the top-level Makefile and
`-Ihypervisor/common/psci` to the include path; `#include <psci.h>` in `vmexit.c`.

## 5. Design Decisions

### 5.1 PSCI as an HVC dispatch slot vs a separate SMC path

**Decision:** Dispatch PSCI from the existing HVC handler, distinguished by the
SMCCC service byte (`0x84`/`0xC4`). **Rejected:** a dedicated SMC conduit / separate
trap path. **Why:** M1 already reserved the PSCI slot in `handle_hvc`; routing by
service byte reuses the existing plumbing with no new entry path, and HVC is a valid
SMCCC conduit. **Revisit when:** a guest expects the SMC conduit specifically, or
EL3 firmware PSCI must be forwarded.

## 6. Acceptance Criteria

1. **Build**: `make` succeeds with zero warnings; `build/obj/common/psci/psci.o`
   exists.
2. **Functional**: a guest that issues `HVC PSCI_VERSION` and prints the result
   observes `0x00010001`. (Reuses the M1 SVM harness with one added HVC.)
